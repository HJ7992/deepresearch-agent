# 用 LangGraph 搭一个「有据可查」的调研 Agent：四个关键设计与踩坑

> 公众号/掘金/知乎投稿初稿。数字待评测跑完后填入（标记为「待填」）。

## 为什么又做一个 deep research agent

2026 年，「输入问题、自动检索、输出报告」的 demo 已经烂大街。但真正拿去用的
时候，你会发现三个问题没人回答：

1. 报告里的话**有没有出处**？模型编一个 [3] 你也看不出来。
2. 长流程跑一半**挂了怎么办**？总不能从头再烧一遍 token。
3. 换个模型（尤其是国产端点）**接口就不兼容**，demo 直接跑不起来。

这篇文章讲我在 LangGraph 上把这三点做实的四个设计，以及踩过的坑。

## 一、Send 并行之后，引用编号会串

多 Agent 调研的第一反应是：planner 拆子问题，researcher 每个子问题检索一次。
串行跑太慢，于是用 LangGraph 的 `Send` 动态扇出——子问题数量运行期才知道，
静态边表达不了：

```python
def fan_out(state):
    return [Send("researcher", {"sub_question": q}) for q in state["sub_questions"]]
```

坑在于**引用编号**：每个并行 researcher 都从 `[1]` 开始给自己的资料编号，
合并后两个任务的 `[1]` 指向不同来源，writer 引用错、verifier 也会误判。

解法是加一个 `collect` 节点：按子问题顺序归并，按 chunk id 去重，
建立 `旧编号 → 新编号` 映射，重写笔记里的编号。这里有个细节——直接 replace
会连锁污染：`[1]→[2]` 之后，原本的 `[2]` 又在下一轮被改成 `[3]`。正确做法是
两段式占位符：先 `[1]→⟦1⟧`、`[2]→⟦2⟧`，再把 `⟦n⟧→[n]`。

## 二、verifier 要用程序，不要用「再问一次模型」

引用核验我做成纯程序节点：

- 正则 `\[(\d+)\]` 抽取报告里的引用编号；
- 编号不在本次检索结果里 → **编造引用**，一票否决；
- 按段落统计「有有效引用的结论」占比 → 覆盖率；
- 覆盖率低于阈值 → 打回 writer 重写（修订轮数封顶）。

路由条件同时看四件事：critic 通过、覆盖率达标、无编造引用、人工审核未退回。
这样做的价值是**确定性**：同样的报告，判定结果永远一样，能进 CI、能被复现；
而「让模型检查模型」既会漂移，也天然偏袒自己。

## 三、换模型就崩：结构化输出的三级降级

用 DeepSeek 跑的时候连撞两次 400：

- langchain 1.x 的 `with_structured_output` 默认走 `json_schema`，端点不支持；
- 改成 function calling，DeepSeek 的思考型模型又不支持强制 `tool_choice`；
- json_mode 还要求提示词里出现 "json" 字样。

最后的方案是一条自动降级链：`function_calling → json_mode → prompted`，
按错误关键词识别「端点不支持」并切换，成功后记住可用模式；json_mode 失败时
自动补 schema 提示。换任何 OpenAI 兼容端点都不用改代码——这比「只支持 OpenAI」
的 demo 更接近真实工程。

## 四、人工审核与断点续跑，是同一个机制

HITL 用 `interrupt()` 实现：审核节点把当前报告抛给调用方，图暂停；
恢复时用 `Command(resume={"approved": False, "comment": "..."})`，
退回意见进入 `critique`，路由自动打回 writer。

这个暂停之所以能跨进程，是因为 checkpoint：每一步状态按 `thread_id` 落库
（本地 SQLite，生产可换 Postgres）。实测把进程杀掉，换一个新进程用同一个
thread_id 恢复，只会执行审核之后的节点（critic），前面的规划、检索、写作
不会重跑——**花的钱不白花**。

## 五、评测：别只看一次演示

固定 20 题评测集，覆盖 RAG / LangGraph / MCP / Agent 评测四个主题；每题带
期望关键词，用规则判定任务是否成功（关键词命中 ≥0.5、覆盖率 ≥0.6、
无编造引用）。另做两组消融（各 6 题）：关掉检索、关掉引用强制，对比指标。

| 模式 | 题数 | 任务成功率 | 关键词命中 | 引用覆盖率 | 编造引用率 | 平均 tokens |
|------|------|-----------|-----------|-----------|-----------|------------|
| full | 20 | 100% | 97% | 92% | 0% | 18,864 |
| no_retrieval | 6 | 0% | 74% | 0% | 50% | 11,642 |
| no_verify | 6 | 100% | 94% | 92% | 0% | 18,953 |

两个值得说的观察：

1. 关掉检索，覆盖率直接归零，一半报告开始编造引用，critic 全部否决——
   想做「可溯源」，检索不是可选项。
2. 关掉引用硬门槛，指标居然没变差。诚实地说：在这套语料上，写作提示词和
   critic 已经把引用质量兜住了；verifier 硬门槛的价值不是抬高平均分，而是把
   「是否合规」从概率判断变成确定性判定——编造编号必然被拦、必然触发重写，
   这条路径由单元测试覆盖，而不是靠跑分体现。

（题数不同，比率不要直接横比；消融用的是同一批题的前 6 题。）

## 结语

项目完整代码、评测脚本、演示语料都在仓库里，`uv sync` 之后三条命令即可复现。
如果你也在做 Agent 项目，建议先把「可溯源」和「可恢复」做掉，再谈功能多少。
