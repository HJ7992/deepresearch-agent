# 改进计划：本次重构没提、但值得做的点

> 本文列的是「除了你交代的简化 / 注释 / 文档之外，我读代码时发现的改进点」。
> **都还没实施**，按「收益 ÷ 成本」从高到低排，每项写清现状、改法、如何验证。
> 带 ⚠️ 的是真实缺陷或隐患，不只是优化建议。

## P0：先修隐患（半天内能做完）

### 1. ⚠️ API 的任务表是进程内字典，多 worker 会不一致

- **现状**：`api._runs` 是全局 dict，无锁。`uvicorn --workers 2` 或以后上 gunicorn 时，
  `POST /research` 落到 A 进程、`GET /runs/{id}` 落到 B 进程就会 404；两个线程同时
  写同一条记录也没有保护。
- **改法**：任务表抽成 `RunStore` 接口，先给一个带 `threading.Lock` 的内存实现，
  再给一个 Redis / SQLite 实现（run_id 做主键，TTL 一天）。启动时按环境变量选实现。
- **验证**：加测试「两个 store 实例共享同一后端时能读到同一 run」；本地
  `--workers 2` 手工跑一遍提交+轮询。

### 2. ⚠️ 结构化输出的降级结果没有跨节点复用

- **现状**：`StructuredCaller` 用 `self.modes.pop(0)` 记住可用模式，但每个节点工厂都
  `new` 一个实例（planner 一个、critic 一个）。于是同一端点上「不支持 tool_choice」
  这类失败会被每个节点各踩一次，日志里出现两条自动降级。
- **改法**：把「当前端点可用模式」提到模块级（`_probed_modes: list[str] | None`），
  或做成一个小类 `ModeProbe` 由 `build_graph` 注入，所有节点共享。
- **验证**：现有 `test_falls_back_to_json_mode_when_tool_choice_unsupported` 扩展成
  「planner 降级后 critic 直接走 json_mode，不再失败一次」。

### 3. ⚠️ 并行 researcher 没有并发上限

- **现状**：`Send` 扇出几个子问题就同时发几个请求。planner 上限 4 个子问题，暂时不致命；
  但接上「每子问题多次检索重试」或更小的并发配额（有的端点并发 1）就会 429。
- **改法**：在 `make_researcher` 外面套一个模块级 `threading.Semaphore(MAX_CONCURRENCY)`，
  或把扇出改成「分批 Send」。
- **验证**：假模型里加 `threading.active_count` 断言并发不超过上限。

### 4. 检索每次都先 `count()` 再查询，多一次往返

- **现状**：`VectorStore.search` 先 `count() == 0` 判断空库。服务端模式下这是一次额外 RPC，
  而空库时 `query_points` 本来就会返回空列表。
- **改法**：直接查，空的自然返回 `[]`；本地模式如需提前返回，把 count 缓存进实例。
- **验证**：`test_search_on_empty_corpus_returns_empty` 应仍然通过。

## P1：质量与成本（值得排一轮迭代）

### 5. 覆盖率粒度太粗：一段里有一个引用就算「有据可查」

- **现状**：`verifier` 按空行切段落统计。一段里 5 句话只有 1 句带引用，仍记满分。
  这是覆盖率长期停在 92% 左右、但读者仍会看到无出处句子的原因。
- **改法**：先按句子切（`。`/`.`/`!`/`?` 加长度过滤），再统计「带引用的句子 / 结论句子」。
  同时把 `MIN_CLAIM_CHARS` 从硬编码改成按语言设定的常量对（中文 12 / 英文 40）。
- **验证**：新增 3 个 verifier 用例（部分引用段、纯中英混合、超短句过滤）；
  用现有 20 题评测对比覆盖率变化，注意这是「变严格」而不是「变差」。

### 6. 没有预算熔断，只有轮数熔断

- **现状**：`max_revisions` 限制修订轮数，但如果单次 prompt 特别长（notes 全量塞进
  writer），一次就可能烧掉几千 token。`UsageTracker` 只是记账，不参与决策。
- **改法**：给 `UsageTracker` 加 `max_total_tokens`，`on_llm_end` 里超阈值就置标志；
  路由函数看到标志就直接 `END` 并标注 `budget_exceeded=True`。
- **验证**：假模型喂超长 usage，断言第二轮不再调用 writer。

### 7. notes 全量塞给 writer，长文档会挤爆上下文

- **现状**：`writer` 把 `"\n\n".join(notes)` 全都塞进 prompt。4 个子问题 × 长片段时
  prompt 会很大且信息重复。
- **改法**：按 token 预算截断（优先保留带引用的句子），或对每段笔记先做一次轻量摘要。
- **验证**：加一个「notes 超预算时报告仍能生成且引用编号不丢」的用例。

### 8. 评测判据可以再加一层「引用是否真支持论断」

- **现状**：规则判定只看关键词命中 + 覆盖率 + 无编造编号。编号存在但内容不相关的情况
  判不出来。
- **改法**：离线批量跑一次「judge 模型」，对每个 `[n]` 判断「该片段是否支持这句话」，
  输出支持率作为**补充指标**（不进 CI 的硬门槛，避免引入非确定性）。
- **验证**：人工抽 20 条标注，算 judge 与人工的一致率，低于 0.8 就先不改判据。

## P2：工程化与体验（有余力再做）

### 9. 类型检查与提交钩子

- **现状**：只有 `ruff check`（E/F 规则），类型注解写得挺全但没有检查器把关。
- **改法**：加 `mypy --strict`（或 pyright）跑 `src/`，先允许忽略 `retriever`/`api`；
  再加 pre-commit：ruff + ruff format + mypy + pytest -q。
- **验证**：CI 增加一步，先在本地把存量错误清零再开 PR。

### 10. 结构化日志与请求追踪

- **现状**：日志是散落的 `logger.info`，没有统一前缀，并发时（多个 researcher 同时打）
  分不清哪条属于哪个任务。
- **改法**：用 `logging.Filter` 注入 `run_id`/`thread_id`，输出 JSON 行；MCP/CLI/API
  各自在入口设置。
- **验证**：跑一次多子问题调研，日志能按 run_id 过滤出完整时序。

### 11. 测试里的剧本假模型应该抽成 fixture

- **现状**：`FakeLLM` / `FakeRetriever` / `FakeStructured` 定义在 `tests/test_fake_graph.py`
  里，新写测试要么 import 测试模块、要么复制一遍。
- **改法**：抽到 `tests/fakes.py`（或 `conftest.py` 里的 fixture），并给
  `_critic_fail_once_llm` 这类「常用剧本」做成工厂函数。
- **验证**：新增测试不用再复制类；`pytest --collect-only` 仍然全绿。

### 12. 文档上传入口（现在只能本地 ingest）

- **现状**：想换语料只能把文件放到 `data/docs` 再跑 CLI。网页端只能提问，不能喂资料。
- **改法**：加 `POST /documents`（multipart），落盘到 `data/uploads` 后走同一条
  `chunk_text` + 索引入库路径；顺手加大小/后缀校验。
- **验证**：API 测试覆盖「上传 → 索引数增加 → 检索能命中」。

### 13. 服务端最小鉴权与 CORS

- **现状**：`/research` 无鉴权、无速率限制；CORS 未显式配置（默认不容跨域）。
  本地演示没问题，一旦暴露到内网就成「免费代币消耗器」。
- **改法**：加可选的 `DEEPRESEARCH_API_TOKEN`（`Depends` 校验 header）；
  用 `slowapi` 做每 IP 每分钟限额；CORS 白名单走环境变量。
- **验证**：无 token 时 401；带 token 正常；超过限额 429。

### 14. 代码导读卡片（配合学习指南）

- **现状**：`docs/学习指南.md` 给了阅读顺序，但「每个文件里哪几个函数是重点」还得自己找。
- **改法**：给 5 个核心文件各写 10 行导读（关键函数 → 一句话职责 → 对应测试名），
  让「读代码 → 跑对应测试」形成闭环。
- **验证**：拿着导读能在 10 分钟内定位「编号重映射」的实现与测试。

## 建议的推进顺序

1. P0 的 1、2、3 —— 都是隐患，改完就补测试，一次性收掉；
2. P1 的 5、6 —— 直接影响「报告可信度」和「花多少钱」，性价比最高；
3. P1 的 7、8 与 P2 的 11 —— 前者影响长文档场景，后者改善后续所有测试的开发体验；
4. 其余按实际要交付的场景挑：对外演示就做 13，要换语料就做 12。

每完成一项，都在 `docs/验收题.md` 里补一道对应的追问——能讲清「为什么这么改」，
比改完更值钱。
