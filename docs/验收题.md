# 验收题（按主题分组）

> 用法：读完代码先自己答一遍，答不上的回代码/文档里找答案。
> 讲之前把这份文件当抽题卡，随机抽 5 道限时口述。
> 题目按「你会在哪个环节被追问」分组，不按开发顺序。

## 一、检索与引用核验

**1. verifier 的引用覆盖率怎么算？为什么不交给 LLM 判断？**
答：按空行切段落，去掉标题与过短的列表项，剩下的正文段落即「结论」；每段用正则
`\[(\d+)\]` 提取引用编号，编号存在于 sources 且不是编造的就是「已引用」；
覆盖率 = 已引用段落 / 结论段落。没有任何可统计段落时按 1.0 处理，避免误伤短报告。
程序化判定确定、可复现、能进 CI；LLM 自评会漂移，同样输入两次结论可能不同。

**2. 为什么放行条件要同时看 critic 结论、覆盖率、无效引用？**
答：三者失效模式不同。critic 管「质量观感」，可能被漂亮的行文骗过；覆盖率管
「是否有据可查」，低覆盖但 critic 满意的情况真实存在；编造编号必须一票否决。
所以条件要全部满足才交付，否则打回重写（有轮数上限）。人工审核结论是第四道
独立条件：人工退回时哪怕 critic 通过也要重写。

**3. 哈希嵌入的局限？生产怎么换？**
答：只做字面相似（字符 n-gram 哈希），不理解语义，同义改写召不回。
嵌入层抽象成 `embed_documents/embed_query`，配好 `EMBEDDING_*` 三项即切换到
OpenAI 兼容的 BGE/text-embedding 服务，检索代码不用改。

**4. 本地嵌入式 Qdrant 和服务端模式的区别？**
答：本地模式 `QdrantClient(path=...)` 把索引存在本地目录，零部署、单进程文件锁，
适合开发/演示/CI；服务端模式连 `QDRANT_URL`，多进程共享、可水平扩展，适合线上。
两种模式共用同一个 `VectorStore`，`get_store()` 按「地址或路径」缓存单例，
本地模式下避免重复打开文件锁。

## 二、并行扇出与状态合并

**5. Send 扇出后为什么需要 collect？不做重映射会怎样？**
答：每个 researcher 各自从 `[1]` 编号，合并后编号必然冲突：两个任务都写 `[1]`，
writer 会引用到错误的来源，verifier 也可能把重复编号当成同一处。
collect 按子问题顺序合并、按 chunk id 去重、把局部编号重映射为全局编号
（两段式占位符替换，避免 `[1]→[2]` 之后又被 `[2]→[3]` 连锁替换）。

**6. `findings` 为什么需要 reducer？其他字段为什么不需要？**
答：并行 researcher 在同一个超级步里各自返回 `findings`，没有 reducer 就会互相
覆盖，所以用 `operator.add` 追加合并。其余字段（`report`、`critique`、`revisions`）
每一步只有一个写入者，后写覆盖即可。状态字段保持这种「单一写入者」约定，
checkpoint、调试和消融实验都会简单很多。

**7. max_revisions 的语义？为什么是 `>` 不是 `>=`？**
答：max_revisions 计「修订轮数」，writer 最多跑 1 + max 次。critic 每审一次
`revisions` 加一；用 `revisions > max_revisions` 判断，是因为第一轮审查
（revisions=1）在 max=1 时应允许一次修订，第二轮（2）才强制停止。写成 `>=`
会导致一次修订都跑不了。

## 三、人工审核与断点恢复

**8. HITL 用 `interrupt()` 的实现原理？暂停期间状态在哪？**
答：`human_gate` 节点里调用 `interrupt(payload)`，LangGraph 抛出中断并保存当前
状态到 checkpointer，`invoke` 返回带 `__interrupt__` 的结果；恢复时用
`Command(resume=decision)` 重新进入该节点，`interrupt()` 的返回值就是 decision。
状态在 SQLite/Postgres（按 thread_id），不在内存里。

**9. 进程被杀后怎么恢复？为什么新进程只跑 critic？**
答：checkpoint 每步落库；新进程用同一 thread_id 调用 resume，LangGraph 从最后
完成的超级步之后继续，已完成的节点不会重跑。所以恢复后只执行 human_gate 之后
的节点（critic），前端规划/检索/写作不重复花钱。测试
`test_checkpoint_survives_restart` 就是模拟这件事：新 app 只发生 1 次结构化调用。

**10. 为什么没上向量记忆（mem0 之类）？**
答：先把价值验证清楚再堆功能。当前用 checkpoint 的 thread_id 已经能做「续问」
级记忆，足以验证「记忆有没有用」；引入向量记忆会改变状态模型、增加召回噪声，
而项目还没有能评估它的评测维度。等评测框架能覆盖「跨会话记忆收益」再决定，
避免没有指标就加复杂度。

## 四、结构化输出与循环控制

**11. 三种结构化输出模式的区别？为什么要自动降级？**
答：`function_calling` 用工具调用约束格式（最精确，但部分端点不支持强制
tool_choice）；`json_mode` 用 `response_format=json_object`（提示词里必须出现 json）；
`prompted` 纯提示词 + 正则抽 JSON（最兼容）。降级按错误关键词切换，成功后把不可用
模式从链里移除（记住），保证换端点不用改代码。注意：401/超时这类不该降级，
必须原样抛出，否则真实故障会被伪装成「端点不兼容」。

**12. 修订循环怎么防止无限烧钱？**
答：`revisions` 计数 + `max_revisions` 封顶；token 计量随报告落盘，评测时可直接
汇总单任务成本；预算敏感场景还可以调小 `max_revisions`。封顶后即使不满意也把
最新一稿交出去，而不是无限重写。

## 五、评测与消融

**13. 评测集为什么用规则判定而不是让模型自评？**
答：任务成功率由「关键词命中 + 引用覆盖率 + 无编造引用」三个可复现的规则算出，
同一份报告任何人跑都一样；模型自评会漂移、无法复现，且容易自我偏袒。
LLM 评审（critic）作为补充信号单独记录，不作为唯一判据。

**14. 任务成功率是怎么定义的？阈值怎么定？**
答：success = 关键词命中率 ≥ 0.5 且 引用覆盖率 ≥ 0.6 且 无无效引用编号。
阈值是工程取舍：太低会把「看着像」算成功，太高会让合理的长尾回答被判失败；
0.5/0.6 是先验设定，后续用人工抽检校准。指标定义都在脚本里，可随数据调整。

**15. 消融实验怎么设计？两组消融分别证明了什么？**
答：一次只改一个变量，在同一批题上对比。关检索组证明「没有资料时覆盖率
归零、关键词命中下降」——检索是引用的前提；关引用强制组证明「没有硬门槛时
编造引用/低覆盖不会被拦下、也不会触发重写」——verifier 与路由条件是质量的
守门员。两组都用同一评测脚本跑，数字可复现。

**16. 为什么评测要固定任务集、固定模型版本？**
答：Agent 输出非确定，模型或提示词一换指标就不可比。固定任务集和模型版本，
才能把「改动带来的变化」和「随机波动」区分开；调提示词后重跑同一套题就是回归测试。

## 六、服务化与接入

**17. API 为什么用「提交 + 轮询」而不是同步阻塞？**
答：一次调研几十秒到几分钟，同步接口会占满连接、超时不可控、无法中途查询进度。
提交后立即返回 run_id，后台任务执行，客户端轮询状态。另外要诚实说明：任务表
是进程内字典，进程重启会丢进度，真正可恢复的是 checkpoint（用 CLI 的 --resume）。

**18. Langfuse 在项目里解决什么问题？没有 key 时怎么办？**
答：把每次 LLM 调用上报成 trace，能看到每个节点的输入输出、token、延迟，
排查「哪一步慢/贵/错」。它是可选依赖：只配了 `LANGFUSE_*` 才挂回调，
没配时用本地 `UsageTracker` + `reports/*.json` 记同样的指标，主流程不受影响。

**19. MCP Server 暴露了哪些工具？为什么 search_docs 和 research 要分开？**
答：`index_status` / `search_docs`（毫秒级检索）/ `research`（几十秒全流程）。
分开是因为 MCP 客户端有超时约束：查资料要快，生成报告要慢；让模型自己选，
避免「只想看资料」就触发一次完整调研（又慢又贵）。

**20. MCP 的 stdio 和 HTTP 传输分别适合什么场景？**
答：stdio 适合本机桌面客户端（Claude Desktop、Cursor）——进程由客户端拉起，
无需端口；HTTP（streamable-http）适合远程/多客户端共享部署，需要鉴权与网络暴露。
本项目默认 stdio，`--http` 切到本地 8001 端口。

**21. 如果对方想现场验证这个项目，你演示哪三步？**
答：① `ingest` + `main` 跑出带引用的报告；② `--review` 演示人工退回与重写；
③ 打开 `reports/*.json` 看 token/耗时/覆盖率。三步命令都在 README 里，可直接复制。
